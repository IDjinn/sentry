# Implementação das fases restantes + Performance + Novas fases de roadmap

Série de commits sequenciais (1 por item), cada um com `cargo fmt/clippy -D warnings/test --all` verde. Os 217 testes atuais nunca quebram.

## Commit 1 — F4.4: Auth + RBAC (server/dashboard)
- `crates/sentry-cli/src/server.rs` + novo `auth.rs`: middleware axum em todas as rotas.
- **Dois mecanismos**: (a) login usuário/senha — hash **Argon2** na config, `POST /login` emitiu cookie de sessão assinado **HMAC-SHA256** (segredo em `[server.auth] session_secret_env`, default `SENTRY_SESSION_SECRET`, expiração configurável); (b) **API tokens** — SHA-256 hash na config com role `admin`/`viewer` (`[[server.auth.tokens]]`, segredo via env).
- RBAC: `admin` = mutações (block/unblock/forgive/resolve/ack), `viewer` = leitura. `mode = "none"|"password"|"token"|"both"` (default none, warning se bind off-loopback sem auth).
- Login page na SPA (`assets/dashboard/`) que guarda o token; logout.
- Deps novas: `argon2`, `sha2`, `hmac`, `rand`. Testes: allow/deny por role, sign/verify de sessão, login flow via `tower::oneshot`.

## Commit 2 — F4.5: Alertas bidirecionais
- Migration `incidents_feedback.sql`: `event_id uuid null UNIQUE` + `acknowledged_at timestamptz`.
- Daemon **auto-cria incidentes** em High/Critical (1 incidente aberto por IP; hoje `incidents().create()` nunca é chamado).
- Webhook: payload ganha `incident_id` + header `X-Sentry-Signature` (HMAC do body com `SENTRY_WEBHOOK_SECRET`); dispatch de actions ganha `ActionContext` via default method no trait `Action` (backward-compatible).
- Endpoints `POST /api/incidents/{id}/ack` (+ resolve já existe) aceitando bearer token admin OU webhook-secret; botão Ack + estado acked na SPA.

## Commit 5 — F3.2: `sentry-source-tcp` (captura + fingerprint)
- Nova crate, capture loop atrás da feature `pcap` (`pnet` opcional no workspace, BPF port filter; requer Npcap/admin — default off, CI não toca nisso).
- Módulos **puros e testados**: fingerprint SYN estilo MuonFP/p0f (`window:options:MSS:scale`; assinaturas masscan/zmap/nmap `65535:::`), reassembler por flow (stream_id = hash do 4-tuple, máquina de estágios Syn/SynAck/Data/Fin/Reset, cap de payload).
- Emite `ProtocolData::Tcp` (campos já existem no core) + novo `SignalKind::TcpScanner` (peso no scorer). Config: `[[source]] type="tcp"` (interface/ports). Modos passive-mirror/tap = mesma crate em capture.

## Commit 6+7 — F3.1 + F3.9: `sentry-edge` (WAF/inline) + modos de deployment
- Nova crate `crates/sentry-edge/` (deps: core; unifica F3.1+F3.9a conforme backlog):
  - Middleware axum reutilizável `sentry_edge::middleware(pipeline, mode)` — Inline (decide antes de proxyar) / Shadow (cópia).
  - Reverse proxy: `[edge]` listen/upstream; verdict→HTTP: Block→403, RateLimit→429, Challenge→página JS challenge; **health-check obrigatório do backend no startup**; body capture `body_capture_kb` (default 0); real-IP precedência §8.1; TLS opcional feature `edge-tls` (axum-server+rustls, cert/key na config).
  - `edge-tcp` (F3.9b): listener TCP inline com verdict/fingerprint no connect, depois pipe para upstream.
- Refactor `daemon.rs`: núcleo do loop (dedupe→process→persist→actions→forks→offender) extraído para struct compartilhada; fan-in vira `enum Incoming { Raw(Event), Processed(ProcessedEvent) }` — o edge roda `pipeline.process()` no mesmo `Arc<Pipeline>` (trackers não duplo-contam) e entrega o resultado pronto.
- Config: `[deployment] mode="passive"|"inline"` (default passive, inline exige opt-in + health-check). Validação de config.
- Docs: seção "Deployment modes" no ARCHITECTURE.md (chain `client → sentry-edge → nginx → app`, critério inline vs passive, alvo ≤50ms), `deploy/k8s/edge-sidecar.yaml`.

## Commit 11 — Performance (F5, parte prática)
- **Benchmarks criterion** (`benches/`): heurísticas, rules, `pipeline.process` end-to-end — baseline antes/depois documentado no ARCHITECTURE.md.
- **Matching SIMD-accelerado**: listas de tokens das heurísticas (SQLi/XSS/traversal/cmd) migradas para `aho-corasick` (uma passada SIMD sobre o texto URL-decodificado, substituindo múltiplos scans).
- **Ring buffer / batching no ingest**: consumer do canal processa em chunks, reduzindo overhead por-evento de lock/task; dedupe LRU sem alocação no hit path.
- Redução de alocações medida no hot path (reuso do `http_text`, formatação lazily). Sem unsafe, sem nightly.

## Commit 12 — Roadmap novo: F5 (perf avançada) + F6 (integrações firewall)
No ARCHITECTURE.md/BACKLOG.md, com critérios e design:
- **F5 Performance Engineering**: eBPF/aya (observação XDP/kprobe, spike Linux), AF_XDP kernel-bypass, io_uring para sources, ring buffers NUMA-aware, kernel module (avaliação honesta de trade-offs vs eBPF), SIMD explícito onde os crates não cobrem.
- **F6 Platform/firewall integrations**: provider **OPNsense/pfSense** (alias tables via REST API / pfctl tables como `ChallengeProvider` — segue o padrão Cloudflare), provider **nginx** (gerador de deny-list include + reload), HAProxy maps, Suricata/fast.log export. `ActionKind` e `build_challenge_action` já suportam novos providers sem mudar regras.
- AGENTS.md (status das fases, contagem esperada de testes), `config/sentry.example.toml` com todas as novas seções (`[server.auth]`, `[deployment]`, `[edge]`, sources novos, feeds de export).

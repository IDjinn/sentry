# F7 — Honeypot paths, Trusted IPs, Firewall bans, Reputation plugins & datasets

Exploração confirmou: as "listas suspeitas" vivem em 3 lugares que precisam ficar sincronizados (`packs.rs`, `heuristics.rs` com prefilter Aho-Corasick, `behavior.rs`); o parser nginx confia em headers de IP **incondicionalmente** (`parser.rs:159-163` — spoofável); não existe execução de firewall no codebase (só `service.rs` com padrão seguro de spawn); o sistema de feeds (`sentry-reputation`, SSRF-guard, `parse_feed`, regras sintéticas `feed:<name>`) é a base para datasets e para a blacklist do AbuseIPDB. O link industrialmonitordirect retornou 403 (conteúdo coberto pelas outras fontes).

## F7.1 — Listas de URLs suspeitas (honey.conf + nginx-ultimate-bad-bot-blocker)

- **Fonte única de verdade** (corrige o problema de sincronização tripla): novo `crates/sentry-core/src/lists.rs` com `SENSITIVE_PATHS: &[(regex, prefilter_literal)]`. `packs.rs::sensitive_path_rules()` e `heuristics.rs` (`SENSITIVE_PATH_RE` + literais SENSITIVE do prefilter) passam a derivar dela — o proptest de cobertura existente continua válido.
- **Adicionar ao pack `sensitive_paths` (enforce)** os paths inequívocos do honey.conf: `_ignition/execute-solution`, `Autodiscover/Autodiscover.xml`, `mifs/.;/services/LogService`, `vendor/phpunit/phpunit/src/Util/PHP/eval-stdin.php`, `HNAP1`, `remote/fgt_lang`, `ecp/Current/exporttool`, `RestAPI/LogonCustomization`, `Telerik.Web.UI.WebResource.axd`, `GponForm/diag_Form`, `wp-includes/.*\.php`.
- **Novo pack default `honeypot_paths` (shadow por padrão)** para padrões largos demais para enforce: `\.aspx$`, `cgi-bin`, `node_modules`, `/actuator/health`. Registrar em `PackMode::all_pack_names()` + `build_default_ruleset` (default shadow).
- **`behavior.rs` DEFAULT_WORDLIST** += `/adminer.php`, `/eval-stdin.php`, `/HNAP1`, `/fgt_lang`, `/GponForm/diag_Form`, `/Autodiscover/Autodiscover.xml`, etc.
- **bad-bot-blocker**: curar UAs de scanner de alta confiança ausentes em `crawlers_bad` (regex do pack + `BAD_CRAWLER_RE` + literais CRAWLER do prefilter); a lista completa (~500) vira exemplo de dataset user_agent (F7.6).
- **Novo pack `host_allowlist` (off por padrão, `params.domains`)**: `header.host` fora da allowlist → Block (referências serverfault/getpagespeed — bloquear conexão não endereçada ao domínio). Parser nginx passa a popular `HttpData.host` a partir do token `http_host`.

## F7.2 — Real IP hardening: trusted_proxies, Cloudflare IPs, TRUSTED_IPS

- Novo `[real_ip]` no config: `trusted_proxies: Vec<String>` (CIDR/IP, default vazio), `cloudflare: bool = true`, `trusted_ips: Vec<String>` (never-ban), `refresh_secs = 86400`.
- **`TrustSet`** (sentry-core, novo módulo `trust.rs`): membership rápido IP∈CIDR, compartilhado via `Arc` entre parser/edge/pipeline.
- **Ranges Cloudflare**: constantes bundled (ips-v4/ips-v6 oficiais) + refresh remoto best-effort em background (falha mantém o bundled).
- **`parser.rs`**: candidatos via header (cf_connecting_ip > true_client_ip > x_real_ip > XFF) só vencem se `remote_addr ∈ TrustSet`; formato sem `remote_addr` mantém comportamento atual (back-compat: quem escreve o log é o edge). Mesma lógica na resolução real-IP do `sentry-edge` (§8.1).
- **`trusted_ips`** (equivalente ao TRUSTED_IPS do nginx-honeypot — "não se trancar fora"): reputação `Authorized` + pipeline trata como Allow + guard never-ban nos actions (firewall/report/blocklist).
- Atualizar `config/sentry.example.toml` e `deploy/honeypot/sentry.toml`.

## F7.3 — Ban types de firewall (nova crate `sentry-action-firewall`)

- **`ChallengeProvider`** (`provider = "firewall"`): herda o filtro Block/Challenge/RateLimit do `ChallengeAction` de graça; um braço novo em `daemon::build_challenge_action`; adicionar ao `sentry-cli/Cargo.toml`. (AGENTS.md §6 documenta exatamente esse fluxo.)
- **Backends com auto-detect** (cacheado, como o getpagespeed faz): **nftables** (recomendado/default: timeout por elemento no set — bans expiram sozinhos, sub-ms, ban em batch via `nft -f` sem fork por IP) → **ipset legacy** (`hash:ip timeout` + `iptables -m set`) → **firewalld** (`firewall-cmd --ipset`). Override: `backend = "nftables"|"ipset"|"firewalld"|"auto"`.
- Layout nft: table `sentry` + sets `blocks_v4`/`blocks_v6` (`flags timeout`) + chain input `priority -1` drop.
- Opções: `ttl_secs=86400`, `rate_limit_ttl_secs=600`, `ban_on_challenge=false`, guard `trusted_ips` (F7.2).
- **Restart-safe/reconcile**: startup garante table/sets + re-seed de `ip_state.blocked()` (reusa o pre-warm existente) + reconcile periódico diff DB↔set (cobre unblock manual via CLI/dashboard/NOTIFY, expiração e multi-node), espelhando o padrão `cloudflare_reaper`.
- **Linux-only em runtime**: fora dele, `build_challenge_action` retorna `Ok(None)` + warn (padrão já usado p/ CF sem token). Command builders e auto-detect puros e testáveis (spawn em arg-list, sem shell, como `service.rs`).
- **Privilégios**: doc com `AmbientCapabilities=CAP_NET_ADMIN` no systemd ou sudoers restrito; nota no template do `service.rs`.
- CLI `sentry firewall status` (backend detectado, tamanho dos sets, último reconcile).

## F7.4 — Plugins AbuseIPDB + ReportedIP (nova crate `sentry-action-report`)

- Nova variante `ActionKind::Report` (action não-edge): `[[action]] type = "report" provider = "abuseipdb"|"reportedip"`, braço em `build_registry`.
- **AbuseIPDB**: `POST /api/v2/report`, header `Key` (env `SENTRY_ABUSEIPDB_KEY`), **categorias mapeadas de SignalKind** (SensitivePath/SQLi→16, BadCrawler→19, RateScan/ScanBehavior/TcpScanner→14, AuthBruteForce→18, LlmMalicious→15…), comment com incident_id, respeito a 429/Retry-After.
- **ReportedIP**: `POST /wp-json/reportedip/v2/report`, header `X-Key`, array de categories das 63 categorias (ex.: 61 Indiscriminate Scan, 59 Honeytoken Triggered), batching (10) + limite 60/min.
- Dedupe LRU por IP (1 report/TTL), `min_verdict` (default "block"), métricas, soft-disable por falhas (padrão CF circuit breaker).
- **Blacklist feed**: `FeedConfig` ganha `headers_env: HashMap<header, ENV_VAR>` → a blacklist do AbuseIPDB (`plaintext=true`, `confidenceMinimum`) vira `[[rules.feeds]] kind = "ip"` para assinantes. Guard SSRF inalterado (Mimosa: http/https + rejeição de localhost/loopback/privado/reservado já implementada no fetcher — reutilizar).

## F7.5 — Check seletivo AbuseIPDB (banda cinza, pós-pipeline/IA)

- Trait `IpLookupProvider` (`sentry-ai`): `check(ip) -> {score 0-100, tier}`; impl AbuseIPDB `GET /check`.
- Config `[ip_lookup]`: `enabled=false`, `provider="abuseipdb"`, `key_env`, gatilho seletivo conforme pedido: **banda de score local** (`score_min=25` até abaixo do threshold de ban), **sinais suspeitos** (`on_signals`), **após LLM** (`after_llm=true`), `cache_ttl_secs=86400`, `max_per_hour` (quota — 1000/dia no plano standard).
- Mecanismo espelha `AiFork`/`LlmFork`: fork async pós-pipeline → novo sinal `ExternalReputation` com peso escalado pelo `abuseConfidenceScore` → `Pipeline::rescore_from` (só eleva, nunca rebaixa); LRU cache por IP.

## F7.6 — Datasets mínimos (kind dimension nas feeds)

- `[[rules.feeds]] kind = "ip"|"user_agent"|"path"` (default `ip`, back-compat total).
- Parse UA/path: linhas simples (skip `#`/vazias) → regra sintética `feed:<name>` com `UserAgent(Regex alternation)` (REGEX_CACHE; o crate regex monta Aho-Corasick internamente p/ alternation de literais) ou `Path` regex; cap de entradas (5000); `action`/`tier` reutilizados; **desativado por padrão** = nenhum dataset embarcado, bad-bot-blocker documentado como URL de exemplo.
- **Roadmap §23 (F7.7)**: datasets DB-backed (tabelas `datasets`/`dataset_entries` + `DatasetRepo`), `sentry datasets import <file|url>` (padrão routes_import), enable/disable por dataset, `NOTIFY sentry_datasets_changed`, prefilter Aho-Corasick dinâmico.

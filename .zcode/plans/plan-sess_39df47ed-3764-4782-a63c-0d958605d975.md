# JS Challenge + rDNS Bot Verification for nginx websites

Goal: add three capabilities following existing patterns — (1) native JavaScript PoW challenge in the inline edge (today `Verdict::Challenge` serves a static 403, `middleware.rs:174-185`), (2) rDNS forward-confirmed bot verification (today `crawlers_good` allowlists by UA only, spoofable), (3) a `ChallengeProvider` "nginx" that generates config for the getpagespeed modules + deny list (roadmap F6.2).

## P1 — Bot verification (rDNS forward-confirm), core + pipeline

**`crates/sentry-core/src/botverify.rs`** (pure, no I/O):
- `BotEngine { Google, Bing, Yahoo, Baidu, Yandex }` with UA patterns (`Googlebot`, `bingbot`, `Slurp`, `Baiduspider`, `YandexBot`) and rDNS suffix domains (googlebot.com/google.com, search.msn.com, yahoo.com, crawl.baidu.com, yandex.com/yandex.net/yandex.ru) — the official reverse-DNS method.
- `BotStatus { Verified(BotEngine), Failed, Unknown, None }`; pure `claim(ua) -> Option<BotEngine>`, `hostname_matches(engine, ptr_host) -> bool`, forward-confirm check `forward_confirms(ip, a_records)`.
- `BotVerifier` = `Arc<RwLock<HashMap<IpAddr, (BotStatus, Instant)>>>` with TTL get/insert + sweep (BlockTable precedent). Verified TTL default 3600s, Failed TTL 600s.
- Async trait `BotDnsResolver` (`ptr(ip) -> Vec<String>`, `a(host) -> Vec<IpAddr>`) — implemented in daemon via **hickory-resolver** (new workspace dep, sentry-cli only; PTR needs real DNS, `tokio::net::lookup_host` can't do reverse). Tests use a mock resolver. DNS only — no new outbound HTTP (SSRF constraint N/A).
- Config `[bot_verification]` (opt-in, `enabled = false`): `cache_ttl_secs`, `failed_ttl_secs`, `timeout_ms = 2000`, `spoofed_weight = 35`, plus which verdict sources feed it.

**Wiring:**
- `Event.bot` field (top-level, same precedent as `Event.reputation` — cross-protocol metadata) + `RuleMatch::BotVerified` DSL condition (`bot_verified = "true" | "false" | "google" | ...`, unified parser like `reputation`).
- Pipeline: before rule eval, if UA claims a bot → check verifier cache; hit → set `evt.bot`, emit `SignalKind::SpoofedBot` (weight 35 → High → Challenge on failure); miss → spawn background verify task (non-blocking; this event stays `Unknown` — no bypass, no signal).
- `crawlers_good` pack: when `bot_verification.enabled`, its `Allow` rules gain `bot_verified = "true"` condition (verified-only allowlist).
- Daemon: construct verifier + hickory resolver, pass `SharedBotVerifier` into pipeline/edge; prune task; metric `sentry_bot_verifications_total{result}`.
- CLI: `sentry bots check <ip> [--ua <agent>]` (mirrors `feeds check`).

## P2 — Native JS challenge in the inline edge

**`crates/sentry-edge/src/challenge.rs`** (pure, testable):
- `challenge_id(secret, ip, bucket) = SHA-256(secret || ip || bucket)` (new `sha2` dep on sentry-edge).
- PoW: client finds nonce s.t. `SHA-256(challenge_id || ":" || nonce)` has `difficulty` leading zero bits (default 16, cap 8..=28) — instant in a browser, impossible without JS.
- Cookie `sentry_ch=<bucket>:<nonce-hex>`; server validation is stateless: recompute challenge for current **and previous** bucket (boundary grace), verify PoW. No DB, multi-node works by sharing the secret.
- `JsChallengeConfig` under `[edge.challenge]`: `enabled = false`, `secret_env = "SENTRY_EDGE_CHALLENGE_SECRET"` (fail-loud at startup if enabled and unset), `bucket_secs = 3600`, `difficulty = 16`, `title = "Verifying your browser..."`.

**Middleware + proxy (`middleware.rs`, `proxy.rs`)** — same flow in both:
- On `Verdict::Challenge` + enabled: parse `Cookie` header → valid PoW cookie → pass through (also stop hardcoding `cookies: None`, populate `HttpData.cookies`); UA-claiming bot + `Verified` in shared verifier → pass through; otherwise → **503** + `retry-after: 3` + embedded challenge page.
- Challenge page: `crates/sentry-edge/assets/challenge.html` via `include_str!` (dark theme matching current pages, no CDN): WebCrypto SHA-256 loop, sets cookie (`Path=/; SameSite=Lax`, `Secure` on https, `Max-Age` = bucket remainder), `location.reload()`. `Block`/`RateLimit` verdicts unchanged (PoW must never unlock a hard block).
- Metrics `sentry_edge_challenge_total{result="served|passed"}`. Tests: PoW round-trip, cookie forgery/replay rejection, bucket-boundary grace, verified-bot bypass, middleware flow.

## P3 — Provider "nginx" (config generation, getpagespeed modules + deny list)

New crate **`crates/sentry-action-nginx/`** implementing `ChallengeProvider` (firewall-crate pattern: pure testable builders + I/O behind provider):
- `Block` (and `RateLimit` if `rate_limit_deny = true`) → generated deny include: `deny <ip>;` lines stamped `# sentry:<ts>:<ttl>` in `<conf_dir>/sentry-deny.conf`.
- `Challenge` → generated `geo $sentry_challenge_ip { default 0; <ip> 1; }` map file; user includes one documented snippet in their server block: `if ($sentry_challenge_ip) { js_challenge on; }` + `bot_verifier on;` (getpagespeed modules installed on the host; works with Sentry running passive — honeypot topology).
- Options: `conf_dir`, `reload_cmd = "nginx -s reload"`, `validate = true` (run `nginx -t` before reload, never reload broken config), `bucket_secs`, `challenge_secret_env`, `provision_bots = true`, `ipv6_prefix` (CIDR entries, parity with CF list mode), `ttl_secs = 86400`.
- Atomic writes (tmp+rename), debounced reload (≥1/s coalescing), TTL reaper task, startup reconcile from `ip_state` (DB = source of truth, firewall precedent), `SharedTrustSet` never-ban guard.
- Daemon: `"nginx"` arm in `build_challenge_action` (daemon.rs:2457); crate added to workspace + sentry-cli. Optional stretch: `sentry nginx status`.

## Objetivo

Refazer as páginas de verdict da edge inline (block/403, 429, challenge) e tornar configurável quem faz o challenge, com status codes idênticos aos do Cloudflare:

- **Página de block hoje** (screenshot): sem ícone, texto "403 — blocked / Your request was blocked by Sentry.", sem ID rastreável.
- **Novo layout** (todas as páginas estáticas de verdict): ícone no topo + título/mensagem + linha `Trace ID:` + rodapé de atribuição, no mesmo tema dark `#0d1117` do challenge PoW.
- **Status codes CF-like**:
  - Block / challenge falhado / challenge interstitial → **403** (o Cloudflare serve o challenge "Just a moment..." com 403 — hoje o PoW responde 503; `Cache-Control: no-store` já enviado elimina a preocupação de cache que motivava o 503 do módulo nginx)
  - Rate limit → **429** (já é)
- **Config `[edge] page_brand`** (enum type-safe, como `ActionKind`):
  - `"sentry"` (default): páginas locais com logo do Sentry, challenge PoW local como hoje (mas 403).
  - `"cloudflare"`: o challenge é **delegado ao plugin Cloudflare** — usa o `ChallengeProvider` existente para adicionar o challenge como regra no CF (o visitante vê a página real do Cloudflare); a edge não serve o PoW local, responde `403 + Retry-After` na requisição corrente até a regra do CF assumir. Páginas estáticas que ainda atingem a origem mostram ícone de nuvem laranja SVG simples + rodapé "Performance & security by Cloudflare".

## Mudanças

### 1. `crates/sentry-core/src/config.rs`
- Novo enum `PageBrand { Sentry, Cloudflare }` com `serde(rename_all = "lowercase")` (typo falha no load, convenção do repo).
- `EdgeConfig` ganha `#[serde(default)] pub page_brand: PageBrand` (+ `Default` impl).

### 2. Novo `crates/sentry-edge/src/pages.rs`
Módulo dono de todas as páginas estáticas de verdict (hoje espalhadas em `middleware.rs`/`challenge.rs`):
- Move `ICON_DATA_URI` + `base64()` de `challenge.rs` para cá; adiciona ícone de nuvem laranja como SVG data URI (sem asset binário novo, sem copiar marca registrada).
- `verdict_page(brand, status, title, message, trace: Option<Uuid>)` — mesmo CSS do challenge (`system-ui`, `#0d1117`, `.icon` 56px, `#8b949e`), linha `Trace ID:` em monospace, rodapé `Performance & security by {Sentry|Cloudflare}`.
- Copys e status exatos (padrão Cloudflare):
  - Block/Quarantine + fast-path: **403** / `403 - Forbidden` / `You are unable to access this website.`
  - Challenge interstitial (PoW): **403** (era 503) / `Verifying your browser...`
  - Challenge sem `[edge.challenge]`: **403** / `403 - Forbidden` / `This resource requires verification. If you believe this is an error, contact the administrator.`
  - Challenge falhado (cookie PoW inválido): **403** / `403 - Forbidden` / `Your browser did not pass the security check.`
  - Retry (brand cloudflare, challenge delegado): **403** + `Retry-After: 3` / `Verifying your browser...` / mensagem de retry
  - Rate limit: **429** / `429 - Too Many Requests` / `Slow down and retry shortly.` (+ `Retry-After: 60`)

### 3. `crates/sentry-edge/src/lib.rs`
- `EdgeRuntime` ganha `page_brand: PageBrand` + builder `with_page_brand()` + getter (default `Sentry`).
- `challenge_gate(headers, ip, trace: Option<Uuid>)`: se `page_brand == Cloudflare`, retorna `Page(pages::retry_page(...))` sem tocar no `JsChallenge` (delegação ao CF); senão fluxo atual, com `failed_response` substituída por `pages::challenge_failed_page` (a `FAILED_HTML` e `JsChallenge::failed_response` são removidas).

### 4. `crates/sentry-edge/src/challenge.rs`
- `CHALLENGE_STATUS`: `SERVICE_UNAVAILABLE` → `FORBIDDEN` (403, CF-like); doc-comments atualizados (a justificativa "503 anti-cache do módulo nginx" é substituída — a página já envia `Cache-Control: no-store`).
- Importa ícone de `pages.rs`; remove `FAILED_HTML`/`failed_response` (movidos para pages.rs).

### 5. `crates/sentry-edge/src/middleware.rs` e `proxy.rs`
- Remover `block_response`/`rate_limit_response`/`challenge_response`/`verdict_page` (só usados entre os dois arquivos; sem uso externo).
- Call sites passam `brand` + trace id:
  - Pipeline Block/Quarantine/RateLimit/Challenge: `Some(processed.event.id)` — o evento é persistido, então o Trace ID é buscável no Postgres/dashboard.
  - Fast-path (BlockTable, sem evento): gera `Uuid::new_v4()`, exibe na página e loga `tracing::info!(trace_id, ip, "fast-path block served")` para ser rastreável nos logs (adicionar `uuid = { workspace = true }` ao Cargo.toml da crate).
- Adicionar header de resposta `x-sentry-trace-id` com o mesmo valor (facilita debug via curl).

### 6. `crates/sentry-cli/src/daemon.rs`
- `.with_page_brand(cfg.edge.page_brand)` nos runtimes HTTP e TCP.
- `page_brand = "cloudflare"`: pular construção do `JsChallenge` (não exige secret) e logar que o challenge está delegado; **warning** no startup se não houver nenhuma action `provider = "cloudflare"` configurada (delegação não terá efeito — visitantes podem ficar em loop de 403).

### 7. Docs/config
- `config/sentry.example.toml`: `page_brand = "sentry"` documentado na seção `[edge]` (explicando os dois modos); textos que citam "stuck on 503" atualizados para 403.
- `ARCHITECTURE.md` §8.3: parágrafo curto sobre páginas de verdict, status codes CF-like, trace id e delegação ao CF.
- `AGENTS.md`: atualizar contagem de testes na seção de status.

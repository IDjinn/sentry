# F3.7 — Reputation feeds (IP reputation / Tor / scanners) + sinal de login suspeito

## Contexto

Avaliação de 10 links externos (FortiGate IP reputation, guia yurisk, IPFire/Shodan, kenwebster/muonfp/p0f, ThreatMetrix) concluiu que o item acionável é o **F3.7 do backlog**, que os links validam: hoje o Sentry tem o esqueleto (`FeedConfig` em config.rs:756, `ReputationTier` em rules.rs:305, `RuleSource::Feed`, DSL `reputation=`, packs `tor`/`vpn_proxy`) mas (a) não há fetcher, (b) `RuleMatch::Reputation` é stub que sempre retorna `false` (rules.rs:435), (c) `SignalKind::TorExitNode`/`KnownBadIp`/`VpnProxy` não têm produtor. Links sobre ThreatMetrix/Pi-Hole e fingerprint TCP (p0f/muonfp) ficam fora do escopo (nota de backlog apenas).

## Fase A — F3.7 core: reputation feeds

### A1. `sentry-core` (puro, sem I/O)
- `event.rs`: adicionar `pub reputation: Option<ReputationInfo>` ao `Event`, com `ReputationInfo { tier: ReputationTier, source: String }` (`source` = nome do feed, ex. `tor_exit`). `#[serde(default)]`; atualizar os poucos pontos de construção literal (`grep "Event {"` nas crates source + fixtures de teste).
- `rules.rs`: implementar `Self::Reputation(tier) => evt.reputation.as_ref().map(|r| r.tier == *tier).unwrap_or(false)` — matching categórico exato (consistente com o DSL `reputation=tor|vpn|...`), não "minimum tier" estilo FortiGate.
- Novo módulo `reputation.rs` (pure): `ReputationStore` — lookup IP→`ReputationInfo` a partir de entradas CIDR v4/v6 (crate `ipnet`, já em `[workspace.dependencies]`); longest-prefix-wins entre feeds conflitantes; API `insert/lookup/len/is_empty`. Parser de feed textual genérico: por linha, primeiro token que parseia como IP ou CIDR vence (separadores whitespace ou `;`), pula comentários `#`/`;;` e linhas inválidas — cobre Spamhaus DROP (`1.2.3.0/24 ; SBL123 ; org`), `check.torproject.org/exit-addresses` (`ExitAddress IP date`), FireHOL netset e lista plana de IPs.

### A2. Nova crate `sentry-reputation` (espelha `sentry-geo`)
- Adicionar ao workspace (`Cargo.toml` raiz + membros).
- Fetcher `reqwest` com: timeout (30s), cap de tamanho (10 MB), `User-Agent: sentry/<ver>`; refresh periódico por feed (`refresh_hours`, default 24); em falha mantém os dados anteriores + `warn` + métrica de falha.
- **Guarda SSRF** (restrição de segurança aplicável): URL somente `http`/`https`; resolver host antes de buscar e recusar localhost/loopback/privado/reservado.
- Expõe `Arc`-shared store (RwLock/ArcSwap) + `refresh()`.
- `config.rs` (sentry-core): estender `FeedConfig` com `tier: String` (default `malicious`) e `enabled: bool` (default `true`); se `action` estiver setada (block|challenge|rate_limit), o daemon gera uma regra sintética `{ match: Reputation(tier), action, source: Feed, tags: ["feed:<name>"] }`.

### A3. Wiring no daemon
- Startup: construir store, fetch inicial de cada feed habilitado, enriquecimento ao lado do geo: `evt.reputation = store.lookup(ip)`.
- Spawn da task de refresh por feed.
- Sinais (produtores para os kinds órfãos, no mesmo ponto do mapeamento pipeline.rs:531): tier `Tor` → `SignalKind::TorExitNode` (peso já reservado 15), `Malicious` → `KnownBadIp` (peso 50), `VpnProxy` → `VpnProxy`.
- Métricas Prometheus: `sentry_feed_entries{name}`, `sentry_feed_last_refresh_ts{name}`, `sentry_feed_failures_total{name}`.
- CLI: `sentry feeds` — status por feed (tier, entradas, último refresh, último erro).
- Dashboard/serialização: `reputation` já serializa no evento (badge de tier no feed de eventos, ajuste mínimo).

### A4. Defaults (opt-in) em `sentry.example.toml`
- `tor_exit` → `https://check.torproject.org/exit-addresses` (tier `tor`)
- `spamhaus_drop` → `https://www.spamhaus.org/drop/drop.txt` (+ edrop) (tier `malicious`)
- `firehol_level1` → `https://raw.githubusercontent.com/firehol/blocklist-ipsets/master/firehol_level1.netset` (tier `malicious`; já contém ranges Shodan/Censys — cobre o caso do link IPFire sem lista manual)
- Packs `tor`/`vpn_proxy` continuam `shadow` por default; com feed presente passam a funcionar de verdade. Tier `vpn` fica para feed fornecido pelo usuário.

## Fase B — Sinal `SuspiciousLoginSuccess` (do guia yurisk)
- `behavior.rs`: IP com ≥N falhas de auth na janela (reusa a janela do `AuthBruteForce`) que obtém **2xx em rota de login** → sinal `SuspiciousLoginSuccess` peso ~45 + incident sempre (webhook) — alertar no sucesso, não na falha (anti-fadiga).
- `[behavior]` em config: `suspicious_success_min_failures` (default 3).
- Sinal emitido **não** rebaixa nem perdoa o histórico do IP.
